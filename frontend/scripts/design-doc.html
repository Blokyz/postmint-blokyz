Technical System Design

PostMint Blocky

Plug-and-Play Post-Mint Set Collection Engine for NFT Projects on Base L2

Document scope: Architecture, data pipeline, rarity & set-generation engine, smart contracts, security model, and forward roadmap
Status: Phase 1 (Rarity Audit) complete · Phase 2 (Set Atlas) generation complete · Phase 3 (Eligibility & Claiming) not started
Date: June 2026

1. System Overview

PostMint Blocky is a plug-and-play set-collection layer for existing NFT projects. A project supplies a contract address; the engine ingests the collection's token and trait data, computes a statistically- and economically-grounded rarity ranking, and proposes a structured set of "collection challenges" (the Set Atlas) across eight rarity tiers. Holders race to assemble and hold the required NFTs long enough to claim a limited number of prize slots per tier, with every claim recorded immutably on-chain.

The system is explicitly not a minting platform — no new NFTs are created, burned, or locked. It is a competitive metagame layered on top of a collection that already exists, designed to re-activate secondary-market trading and community engagement post-mint.

1.1 Core Design Principles

  • Reusable NFTs — holding requirements are checked live; tokens are never burned or escrowed.
  • First-N-wins per tier — each of the 8 rarity tiers has a configurable cap on winning slots; whoever assembles + holds the qualifying set the required duration first, wins a slot.
  • No artificial per-wallet limits — a sufficiently large holder can theoretically win multiple slots in the same tier; this is treated as a deliberate design choice, not a bug (see §9 Open Questions).
  • Minimal, trustless on-chain footprint — only the things that truly need trustlessness (rule commitments, cap enforcement, winner records) live on-chain. Everything computationally expensive (regression, combinatorial search, eligibility scanning) happens off-chain.
  • Project-in-the-loop approval gates — both the rarity ranking and the generated Set Atlas require explicit human approval from the project before they become binding, with UI-driven tuning at each gate.

1.2 High-Level Flow

1. Project supplies NFT contract address + chain | 2. Ingestion: pull all token + trait data (Moralis NFT API v2.2) -> Postgres | 3. Statistical rarity: -log2(trait frequency), normalised to [0,1] | 4. Sales ingestion + wash-trade filtering -> OLS/Ridge regression -> market premium score | 5. Combined ranking = alpha * stat_norm + beta * market_norm (project-tunable weights) | 6. RANKING MANIFEST --[project reviews + approves in UI]--> approved ranking | 7. Set Atlas Generator: slice ranking into 8 rarity bands, derive set rules + feasibility | 8. ATLAS MANIFEST --[project tunes caps/windows + approves in UI]--> approved atlas | 9. Atlas hash committed on-chain via ManifestRegistry (immutable) | 10. Claim event goes live: holders race to assemble + hold qualifying sets | 11. Off-chain watcher tracks holding windows via transfer polling | 12. Backend issues ECDSA eligibility proof once a window completes | 13. Holder submits claim tx -> SetClaimManager verifies + records winner on-chain | 14. Winner manifest exported -> vault partner ships physical prizes

2. Data Pipeline & Rarity Engine

2.1 Ingestion

An async Celery task pulls full token + trait data for a contract via the Moralis NFT API and persists it into Postgres. Ingestion progress is tracked in the ingest_jobs table (status, progress_pct, error_message, manifest_path), allowing the frontend to poll for completion and the pipeline to resume cleanly after a restart.

2.2 Statistical Rarity (Phase 1)

frequency    = token_count / eligible_supply
stat_rarity  = -log2(frequency)          # information-content of a trait value
stat_norm    = (x - min) / (max - min)   # normalised to [0,1] across all trait values

This produces a pure supply-side rarity signal: the rarer a trait value is within the collection, the higher its information content.

2.3 Wash-Trade Detection

Before any price-based signal is computed, the sales history is filtered for manipulated trades. A sale is flagged if any of the following hold:

RuleLogic
Self-tradeseller_address == buyer_address
Pair frequencySame two wallets trade the same token >3× within a 30-day window
Price outlierSale price >10× the rolling 7-day price floor for that token/trait
Quick flipToken re-sold by its buyer within 72 hours

Flagged sales (sales.wash_trade_flag) are excluded from the market-premium regression below, but retained in the database for auditability.

2.4 Market Premium (Phase 1, Step 2)

Model: log(sale_price) = alpha + sum(beta_i * trait_i) + gamma * days_since_first + epsilon

beta coefficient = how much that trait shifts log-price
e^beta           = price multiplier (e.g. beta=2.14 -> buyers pay ~8.5x more)
market_norm      = (beta - beta_min) / (beta_max - beta_min)

Fallback: switch OLS -> Ridge when n_traits > n_clean_sales * 0.5
          (avoids an underdetermined / overfit regression on sparse sales data)

2.5 Combined Ranking

combined_score = alpha * stat_norm + beta * market_norm
Default: alpha = 0.5, beta = 0.5  (project-adjustable via UI sliders)
Sort descending -> rank 1..N

The output is the Ranking Manifest (output/{contract}_ranking_manifest.json), containing the full ranked trait list with stat_norm, market_norm, combined_score, the weighting used, and an approval field that is null until the project signs off via the Audit UI.

Approval gate. The ranking manifest is not binding until a project reviews it in the Audit UI (drag-and-drop reordering supported), adjusts alpha/beta if desired, and explicitly approves it via POST /audit/approve. The Set Atlas Generator (§3) refuses to run against an unapproved ranking manifest.

3. Set Atlas Generator

The Set Atlas Generator (backend/app/atlas/) turns an approved ranking manifest into a structured set of collection challenges across the project's 8 rarity tiers. This is the system's core game-design engine: it must produce challenges that are meaningfully rare but not mathematically impossible.

3.1 The 8 Rarity Tiers

TierDefault CapHolding WindowRank Band (cumulative % of traits)
Common1,000Instant50–100%
Uncommon75024 hours30–50%
Rare50072 hours15–30%
Super Rare2507 days7–15%
Ultra Rare1007 days3–7%
Legendary5014 days1–3%
Mythic1214 days0.2–1%
Secret114 daysTop 0.2%

Caps and holding windows are per-project, per-season configurable defaults — in practice almost every collection needs hand-tuning (see §3.4).

3.2 Pipeline Stages

  • bands.py — slice_into_tiers(): slices the approved trait ranking into 8 disjoint bands using the cumulative rank-% boundaries above.
  • pools.py: DB query helpers — pool_token_count, wallet_counts_for_pool, wallet_owners_for_trait — used to estimate how many wallets can realistically qualify for a given trait pool.
  • rules.py: derives the actual set rule for each tier from one of three archetypes, computes feasibility metrics, and runs ladder detection.
  • generator.py — generate_atlas_manifest(): orchestrates the above into a dict matching schemas/set_manifest.schema.json, merging any per-tier tier_structure overrides supplied by the project.

3.3 Set Archetypes

ArchetypeRuleTypically Used For
Count-of-poolHold any X NFTs from a trait pool of N valuesCommon → Rare
One-of-eachHold ≥1 NFT for each of a fixed small combo of K (2–3) specific trait valuesSuper Rare / Ultra Rare / Legendary
Apex comboHold X NFTs all drawn from the single rarest pool (count-of-pool, scoped to the rarest band)Mythic / Secret

One-of-each: candidate pool vs. fixed combo

For the one_of_each archetype, the tier's full band (e.g. 66 traits for Super Rare) is only the candidate pool — the actual set_rule.trait_values committed to the atlas is a small fixed K=2–3 combo selected from it. A wallet must hold ≥1 token for each of those specific traits to qualify; other traits in the band are not part of the challenge.

_select_one_of_each takes the 8 rarest traits in the band, fetches each trait's owner set via wallet_owners_for_trait, and searches all K=2 and K=3 combinations for the one whose fit_score lands closest to the target of 2.0 (preferring the [1.0, 3.0] range), falling back to the combo with the highest estimated_qualifiers if no combination has a defined fit_score. This search-based selection replaced an earlier version that simply took the 3 globally-rarest traits in the band regardless of whether any wallet could ever hold all 3 — which produced estimated_qualifiers = 0 / fit_score = null for higher tiers on real collections.

3.4 Feasibility Math

max_sets_formable = pool_qualifying_nfts / X
race_intensity    = estimated_qualifiers / tier_cap
fit_score         = 1.0 / |log(race_intensity)|     # target range: 1.0 - 3.0

low_feasibility   = True when fit_score falls outside [1.0, 3.0]
                    (cap drastically over- or under-sized relative to qualifiers)

The target band of fit_score in [1.0, 3.0] roughly corresponds to "estimated qualifiers within a handful to ~20× the cap" — i.e. a real race for a scarce resource, rather than a guaranteed claim or a mathematically empty tier. race_intensity = 1 (exactly one qualifier for one cap slot) is a degenerate case where fit_score is undefined per the function's own docstring — this is expected for a 1-of-1 "grail" Secret tier and is treated as a UI/design question, not a bug.

3.5 Ladder Detection

detect_ladders() checks for >70% Jaccard overlap in trait pools between adjacent tiers with different X values — e.g. "3 Yellow Apes → Common, 6 Yellow Apes → Uncommon". In v1 this is typically empty because band-sliced pools are disjoint by construction; it exists to surface natural escalation chains if/when pool definitions become less strictly band-bound.

3.6 Tuning Workflow

Default tier caps are derived from broad assumptions about trait-distribution width and frequently do not fit a specific collection's actual rarity curve — concentrated collections can produce caps 25–100× larger than the realistic qualifier pool for the rarest tiers, making most slots mathematically unclaimable. The resolution is always manual, project-owner-driven tuning:

  1. POST /atlas/generate produces an initial atlas using DEFAULT_TIER_STRUCTURE.
  2. The Atlas Tier Tuning UI (/atlas, "Set Atlas // Rarity Console") renders all 8 tiers as colour-coded cards (cold-steel → solar-flare gradient, Common → Secret) showing archetype, rule summary, one_of_each trait chips, feasibility metrics, and a fit-score gauge highlighting the [1.0, 3.0] target zone plus a low_feasibility badge.
  3. Each tier card has cap / holding-window sliders, guardrailed to a sensible range around the default (e.g. [default × 0.25, default × 4]), and a "Reset to defaults" action.
  4. A global "Regenerate" button re-POSTs all 8 tier overrides via tier_structure and re-renders with fresh feasibility numbers.
  5. This loop repeats until the project owner is satisfied that every tier sits in (or deliberately outside, for intentional "grail" tiers) the target fit-score range.

This tuning step is explicitly not automated — cap/holding-window decisions are product/business judgement calls that belong with the project owner, not an auto-tuner.

5. Smart Contracts (Base L2)

All contracts target Base L2 (testnet: Base Sepolia, chain id 84532), built with Solidity ^0.8.24, Foundry, and OpenZeppelin 5.x.

5.1 ManifestRegistry.sol BUILT

Locks the approved atlas hash on-chain — an immutable, publicly verifiable proof that the project agreed to a specific set of rules before the claim race began.

lockManifest(nftContract, rankingHash, atlasHash)  -> emits ManifestLocked
verifyAtlas(nftContract, atlasHash)                -> bool
isLocked(nftContract)                              -> bool
Known gap — no access control. Any wallet can currently call lockManifest for any nftContract address. A pre-registration or operator whitelist pattern must be added before mainnet (see §8 Security Model).

5.2 SetClaimManager.sol NOT BUILT

One instance per project per season. Verifies eligibility signatures, enforces tier caps atomically, and records winners on-chain.

claim(tier, qualifyingTokenIds, windowStartedAt, expiry, nonce, signature)

Validation order: tier exists → signature not expired → nonce not used → wallet has not already claimed this tier → cap not full → holding window elapsed → ECDSA signature valid (backend signer) → award slot.

5.3 SetClaimFactory.sol NOT BUILT

Deploys a new SetClaimManager per project/season and acts as a registry of all seasons.

deploySeason(nftContract, atlasHash, backendSigner, tierNames, caps, windows) -> address

7. Eligibility & Claiming (Planned — Phase 3)

7.1 Eligibility Check (per wallet, per tier)

holdings        = current tokens owned by wallet (re-fetched from chain)
matching_tokens = tokens where any trait matches the tier's pool
qualifies       = count(matching_tokens) >= X
progress_pct    = min(100, count / X * 100)
needed          = max(0, X - count)

7.2 Holding Window

Window starts  -> when wallet first qualifies for a tier
Window resets  -> if any qualifying token is transferred OUT
Window expires -> when block.timestamp >= window_started + holding_window_seconds
Window valid   -> backend signs proof -> wallet submits claim tx

Transfer detection is planned via Moralis transfer polling (GET /api/v2.2/nft/{address}/transfers every 30s) — this has no implementation yet and currently blocks the holding-window engine.

7.3 ECDSA Signing (Backend ↔ Contract Bridge)

A backend "hot signer" holds no funds and signs:

wallet + tier + nftContract + tokenIds + windowStartedAt + expiry + nonce

Encoding must match abi.encodePacked() in SetClaimManager exactly. Signatures are valid for 1 hour only, and each nonce is single-use.

8. Security Model

ConcernMitigation
Replay attacksEvery signature includes a unique nonce; the contract stores used nonces
Signature expiryValid for max 1 hour; expired signatures revert with a clear message
Signer compromiseSigner wallet holds no ETH — blast radius is limited to signing ability only
Cap race conditionsclaimed < cap is checked atomically within the same transaction — impossible to exceed on-chain
Cross-chain trustClaims are on Base; NFT data is on Ethereum (for bridged collections). Trust is entirely in the backend signature — must be explicitly scoped in the security audit
ManifestRegistry griefingHIGH Any wallet can currently lock any contract address — must fix before mainnet
Signer key storageMust use a secrets vault in production — never committed to .env in git
External audit required. SetClaimManager.sol must be reviewed by an external security firm before any mainnet deployment.

10.6 Open Product / Design Questions

The Atlas mechanics are implemented and functioning, but the following are business judgement calls awaiting project-owner sign-off rather than engineering blockers:

  1. Rarity band percentages — the tier cumulative boundaries (Secret 0.2%, Mythic 1%, Legendary 3%, Ultra Rare 7%, Super Rare 15%, Rare 30%, Uncommon 50%, Common 100%) are v1 defaults. Do these splits match what should feel rare to collectors across different collections, or do they need per-collection validation?
  2. fit_score target range [1.0, 3.0] — defines what counts as a "healthy race." Is this the right competitiveness target for every tier, or should some tiers be deliberately near-impossible "grails" vs. more inclusive?
  3. one_of_each fixed combo vs. flexible pool — Super Rare/Ultra Rare/Legendary currently commit to one fixed 2–3-trait combo. Should players instead be offered multiple valid combos to choose from?
  4. Race vs. raffle for the rarest tier — Secret/Mythic tiers can have as few as 1–2 possible qualifiers competing for a single cap slot. Is "first to assemble and hold" the right mechanic there, or should it be a lottery among all qualifiers?
